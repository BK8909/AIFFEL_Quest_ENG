# Day 8 자율 프로젝트 — 시니어 안심 문자 분류 API ("이거 봐줘")

## 1. 프로젝트 개요

부모님이 받은 문자·고지서·안내문이 **무슨 내용인지, 조심해야 하는지**를 알려주는 개인 프로젝트 "이거 봐줘"의 분류 엔진을, 사전학습 모델 서빙 형태로 구현했다.

- **도메인:** 시니어(고령층) 대상 문자 해석 — 받은 메시지를 6종으로 분류
- **분류 체계 (6종):** `납부 안내` · `행사 안내` · `개인정보 안내` · `중요한 공지` · `광고` · `사기 의심`
- **출력:** 종류 + 신뢰도 + 부모님용 배지 문구/색(🟢 지금 확인 / 🟡 급하지 않음 / ⚪ 무시 가능 / 🔴 주의)

## 2. 모델 선택 — 왜 zero-shot 인가

| 확인 항목 | 내용 |
|---|---|
| 태스크 | `zero-shot-classification` (NLI 기반) |
| 모델 | `MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7` (한국어 포함 다국어 NLI) |
| 언어 | 한국어 지원 |
| 사용법 | `pipeline("zero-shot-classification")` 한 줄 로드 |

**선택 이유(핵심):** 오늘은 학습이 금지다. 그런데 내 분류 체계(납부/사기 등)는 기성 한국어 분류 모델로 대체할 수 없다 — 감정분류(긍/부정)와는 라벨 축이 완전히 다르기 때문이다. **zero-shot NLI 모델은 `candidate_labels`로 내 6종 라벨을 그대로 주입하면 추가 학습 없이 내 분류 체계가 동작한다.** 즉 "학습 금지 제약 하에서 내 도메인 라벨을 유지하는 유일한 현실적 경로"가 zero-shot이었다.

## 3. 구조

```
app/
├── auth.py            # Day 6 재사용 (X-API-Key 헤더 인증)
├── schemas.py         # PredictRequest / PredictResponse (직접 작성)
├── model_service.py   # load_model() + predict() — zero-shot + 배지 매핑 (직접 작성)
└── main.py            # FastAPI: /health, /predict (직접 작성)
frontend/
└── app.py             # Streamlit 데모 UI (직접 작성)
```

- **비동기 추론:** CPU 추론(블로킹)을 `run_in_executor`로 스레드풀에서 실행 → 이벤트 루프를 막지 않음
- **인증:** `Depends(verify_api_key)` — 키 없으면 401
- **입력 검증:** Pydantic `Field(min_length=1, max_length=5000)`

## 4. 실행 확인 (평가 기준 5개)

노트북(Colab)에서 아래 5개 항목이 모두 정상 동작함을 확인했다.

| 평가 항목 | 확인 내용 | 결과 |
|---|---|---|
| 서버 실행 | `serve_in_thread`로 uvicorn 기동, `GET /health` → `{"status":"ok"}` | ✅ |

## 5. 체크포인트 답변

**Q1. Pydantic 검증은 어떤 잘못된 입력을 막아주는가?**
`text` 필드에 `min_length=1, max_length=5000`을 걸어, ① 빈 문자열(분류할 내용이 없는 요청)과 ② 5,000자를 넘는 과도한 입력을 422로 막는다. 또한 `text`가 없거나 문자열이 아닌 타입이면 FastAPI가 자동으로 422를 반환한다. 덕분에 model_service의 추론 함수는 항상 "비어 있지 않은 정상 문자열"만 받는다고 신뢰할 수 있다.

**Q2. `Depends(verify_api_key)`를 제거하면 어떤 위험이 있는가?**
누구나 API Key 없이 `/predict`를 호출할 수 있게 된다. ① 무단·무제한 호출로 서버 자원(CPU 추론)이 소진되고, ② 비용/부하 통제가 불가능해지며, ③ 사용자 구분이 사라져 남용을 추적할 수 없다. 인증은 "정해진 키를 가진 요청만 추론을 태운다"는 최소한의 접근 통제다.

**Q3. `run_in_executor`를 사용한 이유는?**
transformers 추론은 CPU를 점유하는 **동기(블로킹) 작업**이다. 이를 async 엔드포인트에서 그대로 호출하면 추론이 끝날 때까지 이벤트 루프 전체가 멈춰, 다른 요청(예: `/health`)도 응답하지 못한다. `run_in_executor`로 추론을 별도 스레드풀에서 돌리면, 이벤트 루프는 블로킹되지 않고 다른 요청을 계속 처리할 수 있다.

**Q4. Day 1~8 중 가장 많이 참고한 Day는? 왜?**
Day 6(이미지 분류/챗봇)을 가장 많이 참고했다. `auth.py`(API Key 인증)를 그대로 재사용했고, `Depends`로 인증을 엔드포인트에 붙이는 구조·에러 상태코드 처리 방식이 이번 `main.py`의 뼈대와 가장 가까웠기 때문이다. 스키마·서버 구조는 Day 5(주택 가격 API)도 함께 참고했다.

**Q5. 이 서비스를 실제로 배포하려면 추가로 무엇이 필요한가?**
① **패키징/인프라:** Docker 이미지화 + 클라우드(또는 서버) 배포, 모델 파일 캐싱. ② **성능:** zero-shot은 매 요청 후보 라벨을 모두 평가해 느리므로, 실서비스에선 이 6종 라벨로 소량 데이터를 모아 경량 분류 모델로 **파인튜닝**하면 속도·정확도가 개선된다. ③ **운영:** 요청 로깅·모니터링, 신뢰도 낮을 때의 처리(재질문/사람 확인), 레이트 리밋, HTTPS. ④ **안전:** 오분류가 위험한 영역(사기 미탐)에 대한 임계값·휴먼 확인 장치.

## 6. 회고

이번 프로젝트의 핵심 학습은 **"제약(학습 금지)이 모델 선택의 논리를 만든다"**는 점이었다. 처음엔 감정분류 모델을 쓰려 했지만, 내 도메인 라벨(납부/사기 등)과 축이 달라 프로젝트의 의미가 사라진다는 걸 확인했다. 그 지점에서 zero-shot NLI로 방향을 잡으니 "왜 이 모델인가"가 오히려 명확한 포인트가 됐다.

또한 직접 만들고 있는 개인 프로젝트("이거 봐줘")의 분류 체계와 배지 매핑 로직을 그대로 서빙 구조에 옮기면서, 서비스 로직과 모델 서빙 계층을 어떻게 분리하는지(model_service의 predict가 라벨→배지까지 책임지고, main은 인증·검증·비동기만 담당) 감을 잡았다.

가장 어려웠던 부분은 zero-shot의 특성 이해였다. 라벨을 문장으로 바꿔 NLI로 판별하는 구조라, 후보 라벨 문구를 어떻게 쓰느냐가 결과에 영향을 준다는 점을 알게 됐고, 이는 실서비스로 가면 경량 모델 파인튜닝으로 넘어가야 할 이유이기도 하다.
