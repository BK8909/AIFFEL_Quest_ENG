# Full Stack Deep Learning - Day 1 제출
## Chapter 0 체크포인트

### 1. 모델 배포, Full Stack DL, MLOps는 각각 어떤 범위를 담당하며 왜 분리되어야 하나요?

- 모델 배포는 이미 학습된 모델을 FastAPI, Streamlit 등의 인터페이스를 통해 사용자가 이용할 수 있게 만드는 단계입니다.
- Full Stack DL은 문제 정의, 데이터, 모델, 평가, 배포, 사용자 피드백까지 ML 제품의 전체 생애주기를 다룹니다.
- MLOps는 이 전체 흐름을 안정적으로 반복하기 위한 배포, 모니터링, 재학습, 버전 관리, 자동화 인프라에 초점을 둡니다.

세 과정은 서로 연결되어 있지만 해결하는 문제가 다릅니다. 모델을 사용자에게 전달하는 것, 올바른 ML 제품을 설계하는 것, 그리고 이를 지속적으로 운영·자동화하는 것은 각각 다른 관점과 기술이 필요하기 때문에 분리해서 학습할 필요가 있습니다.

### 2. 평평한 지구 ML과 둥근 지구 ML의 차이는 무엇이며 데이터 플라이휠은 어디에 해당하나요?

평평한 지구 ML은 데이터를 모아 모델을 학습하고 좋은 성능이 나오면 프로젝트가 끝났다고 보는 선형적인 관점입니다.

반면 둥근 지구 ML은 모델을 배포한 이후 실제 사용자의 데이터와 피드백이 다시 데이터 수집과 모델 개선으로 이어지는 순환 구조입니다.

데이터 플라이휠은 이 둥근 지구 ML의 핵심 엔진으로,  
사용자가 서비스를 사용할수록 데이터가 쌓이고, 그 데이터를 이용해 모델을 개선하면서 제품 가치가 높아지는 반복 구조를 의미합니다.

### 3. ML Powered Product와 MLOps의 지향점 차이를 질문으로 대비하면?

- ML Powered Product: "이 모델이 실제 사용자 문제를 해결하고 제품 가치를 만들어 내는가?"
- MLOps: "이 모델을 안정적으로 배포하고 모니터링하며 반복적으로 개선할 수 있는가?"

즉 ML Powered Product는 사용자 가치와 제품 전체가 중심이고, MLOps는 운영의 안정성과 자동화가 중심입니다.
## Chapter 1 체크포인트

### 1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇인가요?

Software 1.0은 개발자가 입력과 출력 사이의 규칙을 코드로 직접 작성합니다. 따라서 특정 기능을 수정하면 어떤 코드가 변경되었는지 비교적 명확하게 추적할 수 있습니다.

Software 2.0은 데이터와 최적화 알고리즘을 통해 모델이 입력과 출력 사이의 규칙을 학습합니다. 코드가 같더라도 데이터, 학습 조건, 하이퍼파라미터가 달라지면 결과가 달라질 수 있습니다.

따라서 Software 2.0은 코드 테스트뿐 아니라 데이터 검증, 모델 평가, 실험 재현, 배포 후 성능 모니터링까지 필요합니다.

### 2. CACE가 전통 소프트웨어보다 ML 시스템에서 치명적인 이유는 무엇인가요?

전통 소프트웨어는 일반적으로 하나의 모듈을 수정했을 때 영향 범위를 어느 정도 예측할 수 있습니다.

ML에서는 데이터의 작은 변화, 피처 하나의 추가, 학습 파라미터 변경 등이 모델 전체의 예측 분포를 바꿀 수 있습니다. 즉 Changing Anything Changes Everything이라는 특성이 강합니다.

따라서 단순히 코드가 실행되는지만 확인해서는 부족하고, 변경 전후의 모델 성능과 데이터 분포까지 함께 검증해야 합니다.

### 3. 기술의 범용화가 ML 엔지니어의 역할을 어떻게 바꾸고 있나요?

과거에는 좋은 모델을 직접 구현하고 학습시키는 능력이 핵심이었다면, 현재는 Hugging Face나 Foundation Model API를 통해 높은 성능의 모델을 쉽게 활용할 수 있습니다.

따라서 ML 엔지니어의 역할도 모델 자체를 만드는 일에서 문제에 적합한 모델을 선택하고, 데이터를 연결하고, 제품에 통합하고, 평가·배포·운영하는 일까지 확장되고 있다고 생각합니다.
## Chapter 2 체크포인트

적용 프로젝트: 시니어 AI Assistant - 부모님이 받은 문자나 사진을 분석해 핵심 내용을 설명하고 필요한 행동을 안내하는 서비스

### 1. 실현 가능성 × 임팩트 매트릭스에서 어느 사분면에 위치하나요?

현재 기준으로는 실현 가능성 높음 × 임팩트 높음에 가깝다고 생각합니다.

문자 분류, OCR, 이미지 이해, 자연어 요약 등 필요한 기능 대부분을 기존 모델이나 Foundation Model API로 구현할 수 있어 기술적 실현 가능성이 높습니다.

또한 디지털 정보 해석이 어려운 사용자가 문자나 안내문을 이해하고 필요한 행동을 빠르게 결정하도록 도울 수 있으므로 사용자 가치도 비교적 명확합니다.

다만 잘못된 안내가 금융·보안 문제로 이어질 수 있으므로 초기에는 완전 자동화보다 보조 도구로 설계해야 합니다.

### 2. "API로 충분한가?"를 판단하려면 무엇을 확인해야 하나요?

다음 항목을 확인해야 합니다.

1. 필요한 정확도를 API가 만족하는가?
2. 호출 비용이 예상 사용량에서 감당 가능한가?
3. 응답 지연시간이 사용자 경험에 적합한가?
4. 개인정보가 외부 API로 전송되어도 되는가?
5. 특정 도메인에 대한 추가 학습이나 세밀한 제어가 필요한가?
6. 외부 API 장애나 가격 정책 변경에 대한 의존성을 감당할 수 있는가?

초기 PoC에서는 API를 이용해 빠르게 가치를 검증하고, 비용·보안·성능 문제가 실제 병목이 될 때 자체 모델이나 Fine-tuning을 검토하는 것이 적절하다고 생각합니다.

### 3. ML 도입 전에 시도해야 할 4가지 대안과 적합한 상황은?

1. 규칙 기반 접근법
   - 명확한 키워드나 패턴으로 충분히 처리 가능한 경우
   - 예: 특정 은행·기관 전화번호나 URL 패턴 탐지

2. Human-in-the-loop
   - 잘못된 판단의 비용이 큰 경우
   - 예: 금융 사기 의심 메시지를 AI가 분류하되 최종 송금 여부는 사용자가 직접 판단

3. Foundation Model API
   - 자연어 이해나 요약 기능이 필요하지만 자체 모델 학습 필요성이 낮은 경우
   - 예: 긴 문자나 안내문을 쉬운 문장으로 요약

4. 전통적 통계 기법
   - 설명 가능성이 중요하고 구조화된 데이터의 관계를 분석하는 경우
   - 예: 사용자 행동 빈도나 서비스 사용량 예측
## Chapter 3 체크포인트

### 1. ML 프로젝트 라이프사이클 4단계와 핵심 활동은?

1. 프로젝트 기획 및 설정
   - 문제 정의, 성공 지표, 리소스와 윤리적 영향을 결정합니다.

2. 데이터 수집 및 레이블링
   - 필요한 데이터를 확보하고 정제하며 신뢰할 수 있는 정답 데이터를 만듭니다.

3. 모델 학습 및 디버깅
   - 베이스라인을 만들고 실험을 반복하며 모델 성능과 오류 원인을 분석합니다.

4. 배포 및 모니터링
   - 실제 사용자 환경에 배포하고 성능과 실패 사례를 모니터링하여 다시 개선 루프로 연결합니다.

### 2. 4단계에서 2단계로 돌아가는 가장 흔한 이유와 예방 방법은?

오프라인 평가에서는 잘 작동했던 모델이 실제 환경에서는 학습 데이터에 없던 입력을 만나 성능이 떨어지는 경우가 가장 흔합니다.

이를 줄이기 위해 기획 단계에서 다음과 같은 질문을 해야 합니다.

- 학습 데이터가 실제 사용 환경을 충분히 대표하는가?
- 예상하지 못한 입력은 어떤 형태로 들어올 수 있는가?
- 실패 사례를 수집하고 다시 레이블링할 방법이 있는가?
- 배포 후 어떤 지표로 데이터 미스매치를 감지할 것인가?

### 3. 데이터 플라이휠이 자연스럽게 형성되는 제품과 인위적으로 설계해야 하는 제품의 차이는?

추천 시스템은 사용자의 클릭, 스킵, 시청 시간 자체가 자연스럽게 피드백 데이터가 되므로 플라이휠이 쉽게 형성됩니다.

반면 시니어 AI Assistant처럼 "AI의 설명이 실제로 도움이 되었는지"가 자동으로 명확하지 않은 서비스는 피드백 구조를 따로 설계해야 합니다.

예를 들어 도움이 됐어요 / 이해하기 어려워요 / 자녀에게 보내기 같은 행동을 기록하면 사용자의 행동 자체가 품질 개선 데이터로 활용될 수 있습니다.
## Chapter 4 체크포인트

### 1. 세 가지 아키타입의 실제 서비스 예시는?

- Software 2.0: 유튜브·넷플릭스의 개인화 추천 시스템
- Human-in-the-loop: AI가 의심 영역을 표시하고 의사가 최종 판단하는 의료 영상 판독 보조
- Autonomous: 인간 개입 없이 운행하는 자율주행 시스템

### 2. Human-in-the-loop에서 Autonomous로 진화하는 경로와 전환 조건은?

초기에는 AI가 결과와 신뢰도를 제시하고 사람이 최종 결정을 내립니다.

사용 데이터와 실패 사례를 충분히 수집한 뒤, 특정 조건에서 모델의 정확도와 안정성이 검증되면 신뢰도가 높은 케이스만 자동 처리하고 낮은 케이스는 계속 인간에게 전달할 수 있습니다.

전환 조건은 단순 정확도뿐 아니라 다음을 포함해야 합니다.

- 충분한 실제 환경 데이터
- 실패 비용을 감당할 수 있는 수준의 오류율
- 신뢰도 추정의 안정성
- 예외 상황과 장애 대응 체계
- 책임 소재와 안전 기준

### 3. 시니어 AI Assistant는 어떤 아키타입이며 이에 따른 전략은?

초기에는 Human-in-the-loop이 가장 적합합니다.

AI가 문자의 의미와 위험 가능성을 설명하고 행동을 제안하지만, 송금·전화·신고 같은 중요한 결정은 사용자가 직접 수행하도록 해야 합니다.

따라서 최고 수준의 완전자율 정확도를 목표로 하기보다 위험한 오답을 줄이고, 불확실한 경우 "확인 필요"로 보내는 방식이 적절합니다.

데이터 플라이휠도 사용자의 수정, 도움 여부, 자녀에게 전달 여부 등을 피드백으로 수집하는 방향이 적합합니다.
## Chapter 5 체크포인트

### 1. ML 프로젝트에 필요한 5가지 역할과 풀스택 ML 엔지니어의 범위는?

1. ML 엔지니어 / Applied Scientist
   - 모델 선택, 학습, 최적화

2. 데이터 엔지니어
   - 데이터 수집, 정제, 파이프라인 구축

3. ML Platform 엔지니어
   - 실험 관리, 모델 레지스트리, 배포 인프라 구축

4. 프로덕트 매니저
   - 사용자 문제와 ML 기술을 연결하고 우선순위 결정

5. 도메인 전문가
   - 데이터 의미 해석, 레이블 기준 설정, 결과 타당성 검증

풀스택 ML 엔지니어는 소규모 프로젝트에서 모델 개발뿐 아니라 데이터 처리, API 서빙, 간단한 인프라와 제품 프로토타입까지 넓게 담당할 수 있습니다.

다만 전문적인 데이터 인프라, 대규모 ML 플랫폼, 깊은 도메인 판단까지 한 사람이 모두 대체할 수 있다는 의미는 아니라고 생각합니다.

### 2. "리서치와 프로덕션의 거리를 좁혀라"는 원칙은 팀의 일하는 방식을 어떻게 바꾸나요?

모델 개발자가 노트북에서 성능만 확인하고 다른 팀에 넘기는 방식보다, 직접 FastAPI나 Streamlit으로 최소한의 프로토타입을 만들어 실제 사용 흐름까지 확인해야 합니다.

이를 통해 모델의 오프라인 성능뿐 아니라 지연시간, 입력 형태, 사용자 경험, 실패 케이스를 초기에 발견할 수 있습니다.

즉 리서치와 제품 개발을 순차적인 전달 과정으로 보기보다, 작은 단위로 함께 반복하는 방식이 필요합니다.
## Chapter 6 체크포인트

### 1. 프로젝트 시작 전 필수 질문 중 가장 답하기 어려운 3개와 이유는?

시니어 AI Assistant 기준으로 다음 세 가지가 가장 어렵습니다.

1) 성공 지표  
단순 분류 정확도만으로 실제 사용자에게 도움이 되었는지 측정하기 어렵습니다. 정확도뿐 아니라 사용자가 이해했는지, 올바른 행동으로 이어졌는지 같은 제품 지표가 필요합니다.

2) Ground Truth 확보  
사기·스팸·공공 안내·일반 메시지 등을 어떤 기준으로 분류할지 명확한 레이블링 가이드가 필요하고, 일부 사례는 정답 자체가 모호할 수 있습니다.

3) 실패 비용  
일반 메시지를 잘못 요약하는 것과 금융 사기 메시지를 안전하다고 판단하는 것은 실패 비용이 크게 다릅니다. 따라서 하나의 평균 정확도로 위험을 평가하기 어렵습니다.

### 2. 고임팩트 프로젝트를 찾는 4가지 멘탈 모델을 적용하면?

예측 비용 하락  
사람이 문자나 이미지를 하나씩 읽고 위험 여부와 필요한 행동을 판단하는 비용을 AI가 낮출 수 있습니다.

마찰 감소  
사용자가 검색하거나 주변 사람에게 물어보는 과정 없이 내용을 업로드하는 것만으로 설명과 다음 행동을 받을 수 있습니다.

Software 2.0  
수많은 키워드와 규칙만으로 처리하기 어려운 다양한 자연어 표현을 모델이 문맥 기반으로 판단할 수 있습니다.

업계 벤치마킹  
스팸 탐지, 피싱 탐지, AI 고객 지원, 접근성 서비스 등 기존 사례에서 어떤 지표와 안전장치를 사용하는지 참고할 수 있습니다.

### 3. 정확도에 9를 하나 추가할 때 비용이 크게 증가한다는 점은 프로젝트에 어떤 의미인가요?

시니어 AI Assistant에서 모든 입력을 99.99% 정확도로 자동 처리하려고 하면 데이터 수집, 검증, 모델 개선 비용이 매우 커질 수 있습니다.

따라서 제품 설계로 요구 정확도를 낮추는 것이 중요합니다.

예를 들어:
- 높은 신뢰도의 단순 안내는 자동 처리
- 위험하거나 불확실한 메시지는 확인 필요로 표시
- 금융·보안 관련 내용은 사용자나 가족에게 재확인을 요구

이렇게 Human-in-the-loop 구조를 사용하면 완전 자율 시스템보다 현실적인 비용으로 서비스를 만들 수 있습니다.

### 4. "당신은 구글이 아니다"라는 원칙에서 지금 필요한 도구와 나중에 필요한 도구는?

지금 필요한 것
- Jupyter/Colab 기반 실험
- 간단한 데이터셋과 평가 코드
- Foundation Model API 또는 기존 사전학습 모델
- FastAPI
- Streamlit
- Git 기반 버전 관리
- 수동 또는 단순 로그 기반 피드백 수집

나중에 필요한 것
- 대규모 Feature Store
- 자동 재학습 파이프라인
- 복잡한 모델 레지스트리
- 대규모 실시간 A/B 테스트 시스템
- 고도화된 오케스트레이션과 분산 인프라

초기에는 제품의 가치와 핵심 가정을 증명하고, 실제 반복 과정에서 병목이 생긴 부분에만 자동화 도구를 도입하는 것이 적절합니다.
# Day 1 통합 체크포인트

## 1. 왜 오늘 내용이 모델 배포 직후이자 MLOps 직전에 위치하나요?

모델 배포를 통해 모델을 사용자에게 전달하는 방법을 알게 되었다면, 그다음에는 "어떤 문제를 어떤 데이터와 모델로 풀어야 하는가", "실제 사용자 환경에서 어떻게 검증하고 개선할 것인가"를 이해해야 합니다.

이 제품 생애주기가 정의되지 않은 상태에서 바로 MLOps 자동화를 시작하면 잘못된 문제나 불필요한 파이프라인을 효율적으로 자동화하는 결과가 될 수 있습니다.

따라서 배포 기술 → 제품과 ML 라이프사이클 설계 → 반복 운영의 자동화 순서가 자연스럽습니다.

## 2. 시니어 AI Assistant에 오늘의 프레임워크 적용

### (1) ML이 정말 필요한가?

단순 키워드나 규칙으로 처리하기 어려운 자연어와 이미지의 의미를 이해해야 하므로 ML이 필요한 영역이 존재합니다. 다만 단순 전화번호·URL 검증처럼 규칙으로 충분한 부분은 ML을 사용하지 않습니다.

### (2) Build / Buy / API 중 무엇인가?

초기 PoC는 Foundation Model API + 기존 OCR/분류 모델을 조합하는 방식이 가장 적합합니다.

빠르게 사용자 가치를 검증한 뒤 비용, 개인정보, 지연시간이 병목이 되면 Fine-tuning이나 자체 모델을 검토합니다.

### (3) 아키타입은?

초기에는 Human-in-the-loop입니다.  
AI는 설명과 위험 신호를 제시하고 중요한 행동은 사용자가 최종 결정합니다.

### (4) 실현 가능성 × 임팩트는?

높은 실현 가능성 × 높은 임팩트 영역을 목표로 합니다. 필요한 기반 기술은 이미 존재하지만 실제 사용자 환경의 평가와 안전성 검증이 중요합니다.

### (5) 비용의 3대 동인은?

- 데이터 가용성: 실제 문자·이미지와 신뢰할 수 있는 레이블 확보
- 정확도 요구: 금융·보안 영역에서 높은 안전성 요구
- 문제 난이도: 다양한 표현과 새로운 사기 유형 등 분포 변화 대응

### (6) PoC 종료 조건은?

- 규칙 기반 베이스라인보다 의미 있는 품질 향상이 있는가?
- 실제 사용 사례를 대표하는 샘플에서 위험한 오답이 허용 가능한 수준인가?
- 응답 시간과 API 비용이 실제 서비스 범위에서 감당 가능한가?
- 사용자가 결과를 이해하고 행동으로 이어갈 수 있는가?

위 조건을 만족하면 다음 단계로 진행하고, 그렇지 않으면 문제 정의나 범위를 수정합니다.

## 3. 데이터 플라이휠 설계

사용자 문자/사진 입력 → AI 분석 → 사용자의 확인·수정·도움 여부·자녀 전달 행동 → 실패 사례와 피드백 축적 → 평가 데이터 및 학습 데이터 개선 → 모델/프롬프트 개선 → 더 정확하고 편리한 서비스 → 사용 증가

특히 사용자가 별도의 복잡한 레이블링 작업을 하지 않아도 도움이 됐어요, 잘못된 결과, 자녀에게 확인 같은 행동이 자연스럽게 품질 개선 데이터가 되도록 설계하는 것이 중요합니다.

## 4. 가장 가능성 높은 실패 시나리오와 예방 방법

가장 가능성이 높은 원인은 프로덕션 환경의 데이터 미스매치로 인한 성능 저하, 즉 기술적 실현 가능성이 아니라 실제 데이터와 평가 설계의 문제라고 생각합니다.

PoC에서는 잘 동작해도 실제 사용자는 예상하지 못한 형태의 문자, 사진, 신조어, 새로운 사기 패턴을 입력할 수 있습니다.

이를 예방하기 위해:
- 실제 사용자 데이터를 최대한 대표하는 평가셋을 만들고
- 위험도가 높은 케이스를 별도 평가하며
- 실패 사례를 수집할 수 있는 피드백 구조를 초기부터 포함하고
- 완전 자동화가 아닌 Human-in-the-loop으로 시작합니다.

## 5. 배포 6개월 후 예상되는 기술적 부채는?

가장 위협적인 것은 데이터 드리프트와 외부 세계의 불안정성이라고 생각합니다.

사기 메시지나 스팸의 표현 방식은 지속적으로 변하고, 외부 Foundation Model API의 모델 버전·가격·응답 특성도 변경될 수 있습니다.

또한 분류 기준이나 프롬프트 하나를 수정했을 때 다른 유형의 입력 성능까지 달라지는 CACE도 발생할 수 있습니다.

따라서 배포 후에는 주요 카테고리별 품질 지표, 실패 사례, 입력 분포 변화를 지속적으로 확인하고 모델/API 변경 전후에 동일한 평가셋으로 회귀 테스트를 수행해야 합니다.
