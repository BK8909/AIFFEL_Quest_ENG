## Chapter 13 체크포인트

### 1. ML 테스트가 전통 소프트웨어보다 어려운 이유는 무엇인가요?

전통 소프트웨어는 입력과 출력 규칙이 명확한 경우가 많지만 ML은 데이터와 확률적 학습 결과에 따라 동작이 달라질 수 있습니다.

또한 코드뿐 아니라 데이터, 모델, 학습 과정까지 함께 검증해야 하고 같은 코드라도 데이터 분포가 달라지면 성능이 변할 수 있습니다.

정확한 정답 하나를 검사하기보다 허용 가능한 범위와 행동을 검사해야 하는 경우가 많다는 점도 어렵습니다.

### 2. 테스트 수트에서 False Alarm이 위험한 이유는 무엇인가요?

정상적인 변경인데도 테스트가 자주 실패하면 개발자가 테스트를 신뢰하지 않게 됩니다.

예를 들어 실제 데이터 범위보다 지나치게 좁은 경계를 설정하면 정상 데이터가 들어올 때마다 실패할 수 있고, 결국 테스트를 무시하거나 끄게 될 수 있습니다.

### 3. overfit_batches=1 테스트가 실패하면 무엇을 확인해야 하나요?

첫째, 입력 데이터와 레이블이 올바르게 연결되어 있는지 확인합니다.

둘째, loss 함수와 출력 shape이 문제에 맞는지 확인합니다.

셋째, optimizer가 실제 모델 파라미터를 업데이트하고 있는지 확인합니다.

넷째, learning rate가 너무 작거나 너무 큰지 확인합니다.

다섯째, Dropout이나 강한 데이터 증강처럼 암기를 방해하는 요소가 있는지 확인합니다.

각 항목은 작은 배치의 입력, 레이블, loss, gradient, 파라미터 변화량을 직접 출력해 확인할 수 있습니다.

### 4. 데이터 기댓값 테스트에서 느슨한 경계가 중요한 이유는 무엇인가요?

데이터는 자연스럽게 변동하므로 정상 범위를 너무 좁게 잡으면 실제로 문제가 없는 데이터까지 오류로 판단할 수 있습니다.

경계를 실제 데이터 분포보다 약간 여유 있게 설정하면 명백한 이상값은 잡으면서 불필요한 False Alarm을 줄일 수 있습니다.

### 5. 불변성 테스트와 방향성 테스트의 차이는 무엇인가요?

불변성 테스트는 의미를 바꾸지 않는 작은 입력 변화에도 예측 결과가 유지되는지 확인합니다.

예를 들어 문자 메시지에 쉼표나 공백을 추가해도 위험도 분류 결과가 크게 달라지지 않아야 합니다.

방향성 테스트는 의미가 특정 방향으로 바뀌었을 때 예측도 같은 방향으로 변하는지 확인합니다.

예를 들어 단순 안내 문구에 송금 요구와 긴급성을 추가하면 위험 점수가 더 높아져야 합니다.

## Chapter 14 체크포인트

### 1. ML에서 Make it Fast가 Make it Right보다 먼저 필요한 이유는 무엇인가요?

ML은 한 번의 학습과 실험에 많은 시간이 들 수 있기 때문에 실행 속도가 너무 느리면 충분한 실험 자체를 할 수 없습니다.

먼저 코드를 실행 가능하게 만들고 병목을 줄인 뒤 여러 실험을 빠르게 반복할 수 있어야 성능 개선도 효율적으로 진행할 수 있습니다.

### 2. OOM 오류를 해결하는 4단계 전략은 무엇인가요?

첫째, mixed precision을 사용해 메모리 사용량을 줄입니다.

둘째, batch size를 줄입니다.

셋째, gradient accumulation을 사용해 실제 메모리는 적게 사용하면서 큰 배치와 비슷한 효과를 냅니다.

넷째, gradient checkpointing을 사용해 일부 활성화 값을 저장하지 않고 필요할 때 다시 계산합니다.

Adam은 파라미터 외에도 gradient와 모멘텀 추정값 등 추가 상태를 저장하므로 모델 파라미터 자체보다 더 많은 메모리를 사용합니다.

### 3. 프로파일링 결과에 따라 어떤 최적화를 먼저 해야 하나요?

get_train_batch가 전체 시간의 60%라면 데이터 로딩이 병목이므로 num_workers, prefetch, 저장장치 속도, 전처리 비용을 먼저 확인합니다.

training_step이 90%라면 모델 연산이 병목이므로 mixed precision, 모델 크기, batch size, 연산 효율을 먼저 점검합니다.

### 4. 스케일링 법칙의 작은 실험에서 자원 추산까지의 흐름은 무엇인가요?

작은 모델이나 일부 데이터로 여러 크기의 실험을 먼저 수행하고, 자원 증가에 따른 학습 시간이나 성능 변화를 관찰합니다.

그 관계가 일정한 패턴을 보이면 더 큰 실험에 필요한 GPU 수, 학습 시간, 비용을 미리 추정할 수 있습니다.

이를 통해 큰 비용을 쓰기 전에 실험 가능성과 예산을 판단할 수 있다는 비즈니스 가치가 있습니다.

### 5. 최근 프로젝트의 성능 문제를 진단한다면 어떻게 볼 수 있나요?

문자 메시지 위험도와 의도를 분류하는 프로젝트에서는 실제 사용자 문장이 학습 데이터와 다른 표현을 사용할 때 성능 저하가 발생할 가능성이 높습니다.

이 경우 단순한 오버피팅이나 언더피팅뿐 아니라 입력 분포 변화도 함께 의심할 수 있습니다.

실제 사용 문장을 검증 데이터에 추가하고, 부족한 유형의 데이터를 더 수집하거나 합성 데이터로 보강한 뒤 다시 평가하는 방법을 우선 적용할 수 있습니다.

## Chapter 15 체크포인트

### 1. LLM 기반 시스템을 Accuracy만으로 평가할 수 없는 이유는 무엇인가요?

LLM 출력은 하나의 정답만 존재하지 않는 경우가 많고 문장이 맞더라도 사실성, 관련성, 안전성, 일관성, 표현 품질이 다를 수 있습니다.

따라서 Accuracy 외에도 사실성, 관련성, 일관성, 안전성, 유용성 같은 평가 차원이 필요합니다.

### 2. LLM-as-a-Judge의 장점과 한계는 무엇인가요?

사람이 모든 결과를 직접 평가하는 것보다 빠르고 많은 샘플을 일관된 기준으로 평가할 수 있다는 장점이 있습니다.

반면 특정 표현, 길이, 순서, 모델 계열을 선호하는 편향이 생길 수 있습니다.

평가 순서를 바꿔 반복하거나 여러 Judge 모델과 사람 평가를 함께 사용하는 방식으로 편향을 줄일 수 있습니다.

### 3. 입력, 출력, 성능 드리프트의 차이는 무엇인가요?

입력 드리프트는 실제 서비스에 들어오는 입력 데이터의 분포가 학습 시점과 달라지는 현상입니다.

출력 드리프트는 모델이 생성하거나 예측하는 결과의 분포가 이전과 달라지는 현상입니다.

성능 드리프트는 실제 정답과 비교했을 때 모델의 정확도나 품질 자체가 떨어지는 현상입니다.

문자 메시지 분석 서비스에서는 새로운 사기 문구나 신조어가 계속 등장할 수 있으므로 입력 드리프트 가능성이 가장 높다고 생각합니다.

### 4. 모델은 시간이 지나면 썩는다는 말은 무슨 의미인가요?

모델이 학습한 현실과 실제 환경이 시간이 지나면서 달라져 기존 모델의 성능이 떨어질 수 있다는 의미입니다.

예를 들어 코로나19 전 데이터를 기반으로 학습한 수요 예측 모델은 코로나19 이후 소비와 이동 패턴이 크게 달라지면서 정확도가 떨어질 수 있습니다.

이를 방지하려면 입력 분포와 성능을 지속적으로 모니터링하고, 기준을 벗어나면 데이터 수집과 재학습을 수행하는 시스템이 필요합니다.

PyTorch Profiler나 Lightning Profiler를 사용해 training_step과 데이터 로딩 시간을 비교하고 GPU utilization과 batch 처리 시간을 함께 확인해 가설을 검증할 수 있습니다.

### 4. 프로젝트를 1페이지로 요약하면 어떻게 설명할 수 있나요?

부모님이나 시니어 사용자가 받은 문자 내용을 입력하면 메시지의 의도와 위험 가능성을 분류하고 필요한 행동을 안내하는 서비스입니다.

사전 학습된 한국어 Transformer를 Fine-tuning하고 FastAPI로 모델을 서빙합니다.

Macro F1을 주요 ML 메트릭으로 사용하고, 실제 서비스에서는 잘못된 위험 판단을 줄이는 것과 사용자가 적절한 행동을 선택했는지를 함께 확인합니다.

데이터, 학습, 테스트, 배포 단계를 분리하고 W&B와 자동 테스트를 통해 실험과 품질을 관리합니다.

### 5. 프로젝트 코드 구조는 어떻게 구성할 수 있나요?

모델 구조와 학습 로직은 LightningModule로 분리하고 데이터 로딩과 분할은 LightningDataModule로 구성합니다.

train.py에서 Trainer를 이용해 학습하고 tests 폴더에 데이터, 암기, 행동 테스트를 분리합니다.

학습 완료 체크포인트는 FastAPI 서버에서 load_from_checkpoint로 불러와 추론에 사용합니다.

## ML 실행 계획서

### Part A. 기획

프로젝트 한 줄 정의:
시니어 사용자가 받은 문자 메시지를 분석해 의도와 위험 가능성을 분류하고 필요한 행동을 안내하는 시스템

ML이 필요한 이유:
같은 단어나 표현도 전체 문맥과 조합에 따라 정상 안내, 광고, 사칭, 금융 위험 등 의미가 달라질 수 있어 단순 규칙만으로 처리하기 어렵습니다.

접근법:
사전 학습된 한국어 Transformer 모델 Fine-tuning

선택 이유:
처음부터 모델을 학습하는 것보다 적은 데이터로 문맥을 이해하는 분류 모델을 만들기 적합하기 때문입니다.

아키타입:
Human-in-the-loop

선택 이유:
위험 메시지를 자동 분류하되 최종 행동은 사용자가 직접 확인하고 결정하도록 하는 것이 안전하기 때문입니다.

비즈니스 메트릭:
위험 메시지 확인 후 적절한 행동 선택률과 오탐으로 인한 불필요한 경고 비율

ML 메트릭:
Macro F1 0.85 이상을 1차 목표로 설정

데이터 소스:
공개 스팸 및 사기 문자 데이터, 직접 수집한 비식별 예시, 합성 데이터

예상 규모:
학습 10,000건, 검증 2,000건부터 시작

레이블:
정상, 광고/스팸, 금융 위험, 사칭/피싱 등 초기 4개 분류

레이블링 방법:
기존 레이블과 수동 검수, 부족한 유형은 합성 데이터로 보완

베이스라인:
키워드 규칙 기반 분류와 TF-IDF + Logistic Regression

주요 리스크:
새로운 사기 표현이 계속 등장해 데이터 분포가 변할 수 있습니다.

위험한 메시지를 정상으로 분류하는 False Negative의 비용이 높습니다.

완화 방법:
실제 서비스 데이터를 지속적으로 모니터링하고 위험 유형별 재현율을 별도로 확인하며 정기적으로 데이터를 추가합니다.

overfit_batches=1 테스트 적용

10분 이내 실행을 위한 조정:
작은 배치와 짧은 최대 토큰 길이를 사용하고 필요하면 모델 크기를 줄여 빠르게 확인

행동 테스트 1:
문장에 쉼표나 불필요한 공백을 추가해도 위험도 분류 결과가 크게 달라지지 않아야 합니다.

행동 테스트 2:
정상 문장에 송금 요구, 긴급성, 계좌 번호 같은 위험 요소를 추가하면 위험 점수가 높아져야 합니다.

PR 단계 테스트:
입력 shape, NaN 검사, 데이터 기댓값 테스트, 작은 암기 테스트, lint

야간 또는 주간 테스트:
전체 검증 데이터 Macro F1, 클래스별 recall, 행동 테스트, 골든 세트 평가

Make it Run 예상 오류:
토크나이저 입력 shape, 레이블 매핑, checkpoint 로딩 오류

Make it Fast 예상 병목:
Transformer 모델 연산

Make it Right 첫 번째 시도:
오류가 많이 발생한 유형의 데이터를 분석하고 해당 데이터를 추가하거나 보강

평가 전략:
자동 메트릭으로 Macro F1, precision, recall을 사용하고 중요한 위험 메시지는 별도 골든 세트와 사람 검수를 함께 사용

모니터링:
입력 드리프트 가능성을 가장 높게 봅니다.

예상 원인:
새로운 사기 수법, 신조어, 문장 형태 변화가 계속 발생하기 때문입니다.
